## 📦 实验内容

- 单文件 `index.html`：纯前端 HTML5 Canvas 实现的**单摆物理模拟器**
- 物理模型：简谐运动角加速度 θ″ = −(g/L)·sin(θ) − c·θ′
- 初始参数：摆长 L = 200 px，重力 g = 9.8，初始摆角 45°
- 交互控制：
  - 摆长滑块（100 ~ 350 px）
  - 重力滑块（1 ~ 25）
  - 阻尼滑块（0 ~ 0.01）
  - 「重置摆动」按钮，点击后摆球精准回到 45°
- 视觉：深色科技背景 `#1a1a24`，摆球带 `shadowBlur` 发光效果

直接双击 `index.html` 即可在浏览器中运行。

## 🪞 人机协同三反思

### 反思一：哪些决策只能我来做？

这次任务 AI 一次性生成了完整的 `index.html`，但有几件事必须由我把关：

1. **验收标准是我读的**——题目要求"双击打开即可流畅左右摆动"、"控制台 0 报错"，这些是判断产物对不对的标尺，AI 不能替我验收。
2. **物理参数是我核对的**——L=200px、g=9.8、初始角 45°、阻尼范围 0~0.01，我对照题目逐项检查了 AI 生成的代码，没有让它"差不多就行"。
3. **Bug 修复的方向是我定的**——题目里特意给了报错信息 `resetAnimation is not defined`，我决定让 AI 把函数显式挂到 `window` 上，而不是改按钮的 onclick 写法。

> 领航员的核心职责不是写代码，而是**说清楚什么叫"做对了"**。

### 反思二：哪些活儿交给 AI 又快又好？哪些必须我盯着？

| 环节 | 交给 AI | 我必须亲自盯 |
| --- | --- | --- |
| Canvas 渲染循环、物理积分公式 | ✅ 一次写出 | 检查公式是不是 θ″ = -(g/L)sinθ，而不是别的近似 |
| 滑块 DOM 绑定、数值实时刷新 | ✅ 全自动 | 拖动滑块时画面是不是真的跟着变（不能只看代码） |
| 发光效果、深色配色 | ✅ 几行 CSS/Canvas | 题目规定背景色 #1a1a24，不能被它自由发挥成别的颜色 |
| "重置按钮点了摆就停"这种运行时 bug | 它能根据报错定位到函数作用域问题 | 修复后我必须自己点一下按钮，看摆是不是真的回到 45° |
| 打 zip、git 提交 | ✅ 全自动 | 压缩包命名 `Week05_Lab_学号姓名.zip` 这种作业规则，必须我盯着文件名对不对 |

> 教训：AI 写的代码看起来都很"漂亮"，但**跑一遍才知道对不对**。特别是题目里专门点出的那个 reset bug，如果我不亲眼看控制台，很容易就漏交了。

### 反思三：这次经历让我对"人机协同"的理解又深了一层

- 上一次（任务一）我体会到的是：**AI 是手脚，人是大脑**。
- 这一次我体会到的是：**AI 不光是手脚，它还是一个能读报错、能自己修 bug 的初级工程师**——它看到 `resetAnimation is not defined` 这种错误，能主动想到"函数作用域没暴露到全局"。
- 但它修完之后，**最后那一下"点一下按钮确认好了"，还是得我来**。AI 不会真的去点那个按钮，它只能"觉得自己应该修好了"。
- 对零编程基础的我来说，这门课最大的收获不是学会了 Canvas，而是学会了**怎么把一句模糊的题目要求，拆成 AI 能执行、我能验收的具体小步**。
